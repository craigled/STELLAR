--------------------------------------------------------------------------------
1. OVERVIEW AND BACKGROUND
--------------------------------------------------------------------------------

STELLAR is a cooperative multitasking virtual CPU and programming layer built
entirely on top of the RCA CDP1802/180X microprocessor. It runs on the Elf2K
board and was written entirely in 1802 machine code — every opcode and operand
byte entered by hand, with all branch targets and addresses calculated manually.
No assembler of any kind was used during its creation.

The project originated during the 2020 COVID lockdown. In Craig Ledbetter's own
words:

  "STELLAR was the result of the 2020 COVID lockdown, and was initially designed
  and created to be a very simple set of general purpose functions that could be
  called to do complex activities on the Elf2K board. It quickly morphed into
  having its own virtual Core CPU structure as a learning platform for me to work
  through all the possible ways I would like an imaginary CPU to function."

The system currently supports up to four simultaneously running virtual machines
(VMs), each with its own registers, accumulators, flags, stack, label table, and
4KB of program memory. STELLAR sits at a level of abstraction above 1802 machine
code but below interpreted BASIC, providing a rich instruction set that handles
16-bit registers, 24-bit and 32-bit accumulators, decimal arithmetic, stack
operations, inter-VM communication, and cooperative multitasking — all on an
8-bit CPU designed in the 1970s.

Current status: Beta, version 0.61. A small number of opcodes remain partially
implemented or have known issues, but the system is a verified working proof of
concept for cooperative multitasking on the 1802.


--------------------------------------------------------------------------------
2. PHYSICAL IMPLEMENTATION
--------------------------------------------------------------------------------

STELLAR is implemented directly in 1802 machine code. Every hex byte was entered
by hand. There is no source file in any assembly language — the hand-written
bytes ARE the source. This means all branch displacements, absolute addresses,
and opcode sequences were calculated manually by the author.

The system uses the CDP1802 SCRT (Standard Call and Return Technique):

  R4 = CALL routine (located at $0340)
  R5 = RETURN routine (located at $0360)
  R3 = main 1802 program counter (as per SCRT convention)

Additional 1802 registers dedicated to STELLAR operation:

  R8 = current VM program counter (points into VM program space)
  R9 = VM stack pointer
  RC = VM core pointer (RC.hi is always maintained as $30 for the active VM)

R8 advancement is a critical discipline in the codebase: every opcode handler
must advance R8 past all bytes of the current instruction (opcode byte plus all
parameter bytes) before returning control to the dispatcher.

The system occupies approximately 12KB of active code in the range $0000-$2EFF,
plus per-VM data areas described in the memory map below.

A notable hardware constraint: short 1802 branch instructions (opcodes $30-$3F)
can only branch within the same 256-byte page. This constrains how opcode
handlers are laid out in memory.

  $2F00-$2FFF   CIDP — Common VM Interchange Data Page (shared by all VMs)

  VM2: core $3400, program $5000

--------------------------------------------------------------------------------
5. CIDP — COMMON VM INTERCHANGE DATA PAGE ($2F00-$2FFF)
--------------------------------------------------------------------------------

The CIDP page is shared across all VMs and holds VM configuration records plus
system-wide state.

Each VM has a 16-byte entry at $2F00 (VM1), $2F10 (VM2), $2F20 (VM3), $2F30 (VM4):

  [00]  VM number
  [01]  Core page address
  [02]  Program location block
  [03]  Maximum program size
  [04]  Timeslice count (instructions per time quantum)
  [05]  State
  [06-09] Command counter (number of instructions executed)
  [0A]  Mode
  [0B]  Status

VM State values:
  00 = Not Available
  01 = Active
  03 = Idle / Waiting
  04 = Paused
  05 = Killed
  0F = Unknown

VM Mode:
  01 = Read Only access
  02 = Read/Write access

VM Status:
  00 = Busy
  01 = Ready
  02 = Error

System-wide registers at $2F50+:
  $2F50  System Interrupt State
           00 = Single (no interrupt)
           01 = HW Interrupt only
           02 = Counter Interrupt only
           03 = Dual (both)
           0E = Error
  $2F51  VM Error Register
  $2F52  Current VM Number (01 to MAX)
  $2F53  MAX VMs (hardcoded 04)
  $2F54  Total VMs currently active
  $2F55  Multitasking Allowed (00 = No, 01 = Yes)
  $2F56  VM Operation (00 = Sequential, 01 = Simultaneous)
  $2F57  VM Repeat (00 = Continuous loop, 01 = Repeat at end)


--------------------------------------------------------------------------------
6. COOPERATIVE MULTITASKING
--------------------------------------------------------------------------------

STELLAR implements cooperative multitasking across up to four VMs using a
command counter timeslice mechanism.

The main scheduler lives at $0050. Each VM is allocated a configurable number
of instruction cycles (the timeslice count stored in its CIDP entry). The
scheduler tracks how many instructions the current VM has executed. When that
count is exhausted, the scheduler:

  1. Saves the current VM's context (R8, R9, and all core register state into
     the VM's core area at +$00E0-$00FF)
  2. Advances to the next active VM
  3. Restores that VM's context
  4. Resumes execution from where that VM left off

Each VM has fully independent state:
  - 16-bit general registers R0-RF
  - Main, Math, and Decimal accumulators
  - All flags (Test, Carry, Overflow, Interrupt, etc.)
  - Call/Return stack (128 bytes)
  - Label array (256 x 2-byte entries)
  - 4KB program memory

The DELAY opcode (C0) is multi-VM aware. In a single-VM environment it blocks
for the specified number of delay units. In a multi-VM environment, each delay
unit causes the VM to yield its timeslice to the other VMs, allowing concurrent
activity during wait states. This prevents one VM's delay from stalling the
entire system.

VMs can share data with each other through the D0-DF inter-VM opcode group,
but only when sharing has been enabled by the D0 (SHAREVM) opcode. Sharing can
be configured as read-only or read/write. The inter-VM opcodes allow copying
accumulators, registers, and individual memory bytes between VMs.

A VM can pause or kill another VM using the CE (PAUSEVM) and CF (KILLVM)
opcodes, providing basic VM lifecycle management from within a running program.

(opcode byte plus one or more parameter bytes). An extended opcode prefix (F8)

opcodes. Non-zero = TRUE, zero = FALSE.

DF = 1 means NO borrow occurred (this is the inverse of intuitive expectation).

--------------------------------------------------------------------------------
8. KEY DESIGN NOTES AND CONSTRAINTS
--------------------------------------------------------------------------------

R8 ADVANCEMENT RULE:
Every opcode handler must advance R8 past the complete instruction (opcode byte
plus all parameter bytes) before returning to the main dispatch loop. Failure to
advance R8 correctly will cause the VM to misinterpret bytes and execute garbage.

GETPARAM ROUTINE ($0400):
The standard operand decoding routine. Mode 01 reads lo-byte pointers; mode 03
reads hi-byte pointers. All multi-byte opcode handlers call this routine to
decode their operand nibbles.

MODIFY_NIBBLE ROUTINE ($0450):
Decodes register-pair parameters (e.g., "XY" notation in the opcode table, where
the single byte encodes two 4-bit register numbers).

TEST FLAG CONVENTION:
The Test Flag at core offset +$0045 is the universal branch condition. All test
opcodes (80-9F) write their result here. Non-zero = TRUE. Zero = FALSE. Conditional
branch opcodes (A0-A9) read this flag.

1802 DF FLAG BEHAVIOUR:
The CDP1802's DF (data flag) behaves counter-intuitively after subtraction:
DF = 1 means the subtraction required NO borrow (i.e., result was non-negative).
DF = 0 means a borrow occurred. This is the opposite of many other architectures
and must be kept in mind when implementing or extending arithmetic handlers.

SHORT BRANCH PAGE CONSTRAINT:
CDP1802 short branch instructions ($30-$3F) can only branch to addresses within
the same 256-byte memory page. This places a hard layout constraint on all opcode
handler code: any handler that uses short branches must fit entirely within, or
carefully straddle, page boundaries. This is one reason the opcode handler space
($0A00-$2EFF) is large and carefully structured.

LABEL STORAGE:
Labels are stored in a 512-byte array at $3200-$33FF (VM1) — 256 two-byte
entries. Each entry holds the 16-bit address corresponding to the label number.
The LBL opcode (B3) writes the current VM PC into the label array. GTL (B4) and
the conditional label branches look up addresses from this array.

MEMORY MODES:
STELLAR supports both absolute and relative memory addressing within VM program
space. The mode is set per-VM via the MEMMODE opcode (20) and stored at core
offset +$003B. In relative mode, memory addresses in data-move opcodes are
offsets from the start of the VM's program block rather than absolute 1802
addresses.

RUNMC OPCODE (C2):
Allows embedding raw 1802 machine code bytes directly within a STELLAR program.
The inline machine code is executed natively by the 1802. The handler must end
with SEP R5 (1802 opcode $B5... actually the SCRT return sequence) to hand
control back to the STELLAR dispatcher.

COMMAND COUNTER:
Each VM maintains a 4-byte command counter at core offset +$0033 that counts the
total number of instructions the VM has executed since starting. This can be read
with the COPYCCA opcode (28) and tested with TESTCCGX (8B).

9. CURRENT STATUS
--------------------------------------------------------------------------------

Version:  0.61 (Beta)
Date:     January 1, 2026
Hardware: Elf2K (RCA CDP1802/180X)
Code size: approximately 12KB of hand-assembled machine code

The system is a verified working proof of concept. Cooperative multitasking
across up to four VMs has been demonstrated. The majority of the 191 defined
opcodes are fully implemented and functional.

A small number of opcodes remain partially implemented or have known issues —
this is the primary reason the version remains at Beta 0.61.

As the author notes:

  Machine Code/Assembly language of the 1802."
